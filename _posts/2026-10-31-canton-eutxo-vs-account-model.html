Canton notes: Canton architecture · eUTXO vs account model in Canton · How Canton achieves decentralization

TL;DR

In the account model a contract is a mutable object at a fixed address; in the eUTXO model a contract is an immutable value that is replaced on every change.

  • Account model (Ethereum): a contract (e.g. a counter) lives at 0xC0FFEE forever. An increment overwrites its storage in place.
  • eUTXO model (Canton): the counter is a chain of versions #A → #B → #C. An increment archives one version and creates the next, with a new contract ID.
  • The root cause is execution order. Ethereum orders transactions first and then executes them against global state. Canton executes first, privately, and then orders, so each transaction must pin its exact inputs.
  • What follows for the backend: stale IDs, contention rejections, re-reads, and modeling a stable business ID in the application.

Submitting a command

One key difference between the two models is whether a transaction is executed before or after it is ordered.

  • Ethereum (order-then-execute): every node holds the global state and re-runs every transaction in block order. A transaction never needs to name a version; concurrent writers are simply serialized.
  • Canton (execute-then-order): no node holds global state, and the sequencer cannot read payloads, so it cannot execute anything. The submitter executes on its local view, which fixes the exact contract versions it consumes before ordering. Stakeholders then only check those versions are still active.
  • Canton gets: privacy (only stakeholders see or validate) and parallelism (disjoint contracts never conflict). At the cost of: client-side retries, due to stale contract IDs.

The counter in the account model (Ethereum)

In the account model the counter is one object at one address, and an increment overwrites its storage in place.

contract Counter {
    uint public value;
    function increment() public { value += 1; }
}
// deployed once at 0xC0FFEE, forever
  • State is a global mutable map: address → {code, storage}. Every full node holds all of it.
  • A transaction names the address: "call increment() on 0xC0FFEE".
  • Execution reads the current value at that moment. Three increments turn storage slot value from 0 to 1 to 2 to 3, and the address never changes.
  • 0xC0FFEE is both the instance and the business object (the real-world thing the application cares about, which keeps its identity while its state changes).

The counter in the eUTXO model (Canton)

In the eUTXO model the counter is a chain of immutable versions, and an increment consumes one version and creates the next.

template Counter
  with
    owner : Party
    name  : Text      -- stable business ID, e.g. "visits"
    value : Int
  where
    signatory owner

    choice Increment : ContractId Counter
      controller owner
      do create this with value = value + 1   -- archive this, create the next
  • UTXO = unspent transaction output. In Bitcoin it is a coin that can be spent exactly once. Extended UTXO (Cardano, Canton) lets that output carry code and data, so it can be a contract.
  • Ledger state is the set of unspent outputs: in Canton, the Active Contract Set (ACS). There is no mutable storage, only create and archive.
  • A transaction names the exact version it consumes: "exercise Increment on #A". That version must still be unspent when the transaction commits.
  • Each increment yields a new contract ID: #A (0), then #B (1), then #C (2), then #D (3). Only the newest one is active.
  • Identity must be modeled: the contract ID names one version. The stable thing the backend tracks is a field like name = "visits".

Three increments in both models

The same three increments leave one object in Ethereum and a chain of four versions in Canton, of which only the last is active.

Each arrow is one increment. In Canton, holding #B after #D exists means holding a dead reference: exercising on it fails.

Backend responsibilities: Ethereum vs Canton

The account model hands the backend identity, so the backend does not need to worry about lookup and serialization. In Canton the backend needs to worry about both.

ConcernEthereum backendCanton backend
Which counter?Hard-code 0xC0FFEEStore a business ID (name) and the last known contract ID
Finding iteth_call on the address, any nodeACS query on the backend's own participant, filtered by party, template and name; or a projection kept from the update stream
After an editNothing changesTake the new contract ID from the exercise result
Concurrent writersSerialized; all succeedFirst wins; others get archived or locked rejections, back off, re-read, retry
Replay protectionAccount nonce: a strict per-sender sequence number; a stuck nonce blocks later transactionscommandId: an idempotency key the backend chooses, per intent; duplicates rejected within the dedup window; no ordering between commands
Did the transaction land?Receipt by transaction hashCompletion matched by commandId, then the transaction by updateId
Two identical countersImpossible: two deployments have two addressesPossible: two creates give two contract IDs with equal payloads. A business ID field makes duplicates detectable.

In short: a Canton contract ID identifies a version, a commandId identifies an intent, and the business ID identifies the thing. In Ethereum, the contract address and the business ID are the same thing.

If two backends increment at once

In the account model both increments succeed and the counter reaches 2; in the eUTXO model the second one is rejected and must re-read and retry.

How the re-read works in the ACS

Where each request goes is shown in Canton architecture.

  1. Read the ledger end: GET /v2/state/ledger-end → offset X. The ledger end is the offset of the newest update this participant has indexed: the head of its local log. Querying the ACS there returns the latest state this participant knows.
  2. Query the ACS at offset X, for example filtered by party and template (Alice, Counter) → only #B comes back. #A was archived by Backend 1, so it is no longer active. 
    POST /v2/state/active-contracts
{
  "activeAtOffset": 10460,
  "filter": { "filtersByParty": {
    "Alice::1220...": { "templateFilters": ["#counter-app:Main:Counter"] }
  } }
}
  3. Filter in the backend: keep the entry whose name == "visits" → #B.
  4. Exercise Increment on #B → #C {visits, 2}. This is a command submission (POST /v2/commands/submit-and-wait): the participant interprets it, then it goes through the sequencer and mediator like any transaction.

Contention

Contention is several in-flight transactions trying to consume the same contract; in the eUTXO model only one can win, and the others are rejected.

The shaded band is the lock window: from the moment T1 is validated until its verdict, the participant holds #B locked. Any other transaction on #B in that window is rejected as locked; any transaction after the commit is rejected as archived, because #B no longer exists.

RejectionWhat it meansWhat the backend does
LockedAnother transaction on the same contract is in flight; it may be accepted or rejected, so the contract may end up active or archived. So the transaction is locked out, and will probably be rejected in the future.Back off briefly, re-read, retry
Archived / not foundAnother transaction already consumed the contractRe-read to find the successor, then retry

Account model contrast: in Ethereum, a hot contract never rejects; every call to 0xC0FFEE is queued in block order and executed against the latest state. Contention costs are replaced by ordering costs (gas bidding, waiting for inclusion).

Why a counter is the worst case: every increment consumes the same contract, so throughput is capped at one committed increment per lock window, no matter how many backends submit.
