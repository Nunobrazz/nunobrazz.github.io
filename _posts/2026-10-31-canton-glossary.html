Canton notes: Canton architecture · eUTXO vs account model in Canton · How Canton achieves decentralization · Canton glossary

Command

The request a backend sends to its participant node: the intent to create a contract or exercise a choice. A command is input only; it never appears on the ledger.

  • Contains: a template and arguments (create), or a contract ID, choice and arguments (exercise), plus metadata: commandId, actAs, readAs, disclosed contracts, deduplication period.
  • Written by: the backend.
  • Identified by: commandId, chosen by the backend.
  • Seen by: the submitting participant only.
ExerciseCommand: exercise Transfer on #X
  commandId: "transfer-42", actAs: Alice

Transaction

The full effect of a command: the tree of actions the Daml engine produces by running it. The transaction is what gets validated and committed to the ledger.

  • Contains: every create, exercise, fetch and archive the choice causes, nested; input contract IDs and newly created ones.
  • Written by: the Daml engine on the submitting participant, by interpreting the command.
  • Identified by: updateId, assigned at commit, plus an offset on each participant.
  • Seen by: each stakeholder sees only its own views, the parts that concern it.
Exercise Transfer on #X   (consuming → #X archived)
 ├─ Create #Y   (new owner's holding)
 └─ Create #Z   (change back to Alice)

The command named only #X; #Y and #Z appear because the choice's code creates them.

  • Several commands, one transaction: a submission can carry a list of commands; they commit atomically, all or nothing.
  • A command, no transaction: interpretation can fail (Daml error, missing authorization, contract not found), or the transaction can be rejected (e.g. contention). Nothing commits; the completion for the commandId reports the failure and there is no updateId.
  • Ethereum contrast: an Ethereum transaction is closer to a Canton command, a signed intent every node executes. In Canton the submitter executes it to build the transaction tree, and each stakeholder re-executes only its own views to validate it.
