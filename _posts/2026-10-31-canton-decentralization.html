Canton notes: Canton architecture · eUTXO vs account model in Canton · How Canton achieves decentralization

TL;DR

Canton needs decentralization at two levels: the protocol level (the synchronizer that orders messages and decides commits) and the application level (shared parties that act for a group). Validation needs nothing extra, because each stakeholder already validates its own views.

  • Protocol level, ordering: sequencers run by different operators agree on one message order with BFT consensus, safe with fewer than 1/3 faulty.
  • Protocol level, commit verdicts: a mediator group delivers a verdict only when a threshold of mediators agree.
  • Protocol level, governance: the synchronizer's identity lives in a decentralized namespace; changing operators or parameters needs a quorum of owner signatures.
  • Application level, shared parties: a decentralized party is hosted on several participant nodes with a confirmation threshold, so no single node can act for it.
  • Application level, rules and liveness: the Daml model encodes how many members must agree (confirmations, votes, medians), and every member runs the same automation.

The Global Synchronizer applies both levels, with the super validators (SVs) as operators and the DSO party as the shared application party.

Overview

On the Global Synchronizer each super validator runs one copy of every role, and each role acts only when a threshold of copies agree.

Each row is one role, with its agreement rule on the left; each column is one operator. The sequencer, mediator and governance rows are protocol-level decentralization; the DSO party row is application-level.

Protocol level: the synchronizer

The synchronizer is the shared infrastructure every transaction passes through, so each of its functions is run by several operators and acts on a threshold.

Application level: decentralized parties

A decentralized application needs a party that no single member controls; the solution is a decentralized party, plus Daml models that govern what the party can do.

Decentralized parties

  • Hosting: a party hosted on n participant nodes with confirmation threshold t. The mediator waits until t of them send the same answer (approve or reject); no single node can confirm or block on its own. t colluding operators could confirm an inactive contract (a double spend) or an action the party never agreed to. The confirmation threshold should therefore be at least the threshold the Daml governance rules expect.
  • Application trust: if necessary, an application can read the same contracts from several hosting participants and check that they agree.

Rules and automation in Daml (Splice example)

On the Global Synchronizer the application layer (Canton Coin, SV governance) is run by the DSO party. Every SV node hosts it, and a single contract, DsoRules, encodes every way it is allowed to act.

Each SV node runs the same SV app automation, which submits transactions through that node's participant, acting as the DSO party with the SV passed as sv. What happens next depends on how much agreement the action needs.

The threshold: requiredNumVotes = ⌈(n + f + 1) / 2⌉, where f = ⌊(n − 1) / 3⌋ is the number of faulty SVs tolerated. With this value, f SVs abstaining cannot block an action (availability) and f Byzantine SVs cannot push one through (integrity).

Two thresholds work together: the Daml rules above decide what the DSO does, while the DSO party's hosting threshold (about 2/3 of SV participants must confirm each DSO transaction) stops any single SV node from submitting a DSO action that the others do not validate.

Guarantees, with at most f faulty SV nodes:

  1. Every transaction that needs the DSO party's confirmation is valid.
  2. DSO actions happen in a timely way.
  3. Fees and configuration reflect the aggregate preferences of about 2/3 of SV operators.
