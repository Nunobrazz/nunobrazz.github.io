Canton notes: Canton architecture · eUTXO vs account model in Canton · How Canton decentralizes

Network view

A Canton network has three layers: backends (applications), participant nodes that host parties and store their contracts, and synchronizers that order messages between participants.

  • Party: an identity such as Alice, hosted on one or more participant nodes.
  • Participant node: stores the ACS of its parties, runs the Daml engine, and exposes the Ledger API to its backends.
  • Synchronizer: sequencer + mediator. It orders encrypted messages and coordinates commits, but never sees contract data. The Global Synchronizer is a public one, run by super validators; a private synchronizer is run by one operator or a consortium.
  • Communication: a backend communicates only with its own participant node; participant nodes communicate with other participant nodes only through a synchronizer they share.

Requests

Every request goes from the backend over HTTP to the JSON Ledger API of its own participant node; only a command submission leaves that node.

Command submission

Network level

The submitter executes; the synchronizer orders; stakeholders confirm by re-executing what they are entitled to see.

The submitting participant runs the Daml code first (step 2) to build the transaction; the synchronizer orders and forwards encrypted views without reading them; each confirming participant re-executes its own views before voting (steps 4–5), and every stakeholder's participant commits the result to its own ACS (step 7).

Step by step

A command that exercises a consuming choice on contract #X crosses every component before the backend gets its answer.

  1. Backend → JSON Ledger API: POST /v2/commands/submit-and-wait with a commandId, the acting party, and the choice to exercise on #X.
  2. Daml engine: loads #X (cache or index DB), runs the choice, builds the transaction: archive #X, create #Y.
  3. Sync protocol → sequencer: encrypted views go out for ordering and a timestamp.
  4. Sequencer → participants and mediator: each stakeholder's participant gets its views; the mediator gets metadata only.
  5. Validation: each stakeholder's participant checks #X is still active in its ACS, locks it, and sends approve or reject to the mediator.
  6. Mediator verdict: commit or reject goes back to every involved participant.
  7. Commit: the ACS journal records #X deactivated and #Y activated; the indexer writes the update into the index DB.
  8. Response: the JSON Ledger API answers the waiting HTTP call with the result, including the updateId and #Y.

All node-to-node messages physically travel through the sequencer; the diagram shows the logical flow. When the acting party is the only stakeholder, step 5 runs on its own participant alone.
